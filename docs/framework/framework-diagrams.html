AI delivery framework

An AI agent team that turns stakeholder requirements into tested, validated and accepted features for a new product, with the backlog kept as files in the project repo. React and Supabase edition.

Built on Claude agents Git (backlog as files) React Supabase Python (AI) Docker

Key principles

Quality gates. A Definition of Ready before work starts and a Definition of Done before human review, so agents never build vague stories and humans never review half-finished work.
Contract first. UI/UX hands over HTML and the architect fixes the data contract (tables, RLS policies, generated TypeScript types) before coding, so frontend and backend build in parallel instead of waiting on each other.
Two assurance agents. A solution architect (design, contracts, code review) and a security and compliance agent: the browser talks to the database directly, so row-level security must be right from day one.
Three loops through the backlog. Review changes, QA bugs and stakeholder feedback are logged in the backlog files and loop back to the owning agent. Each loop re-runs review and QA.
Escalation. A third loop on the same story, or a blocker older than one working day, goes to a human. Agents never spin forever.
Sprint layer. Human-approved two-week planning, a release decision, and a retrospective that improves the agents’ own instructions.
DevOps starts light. Docker stays low priority, but one CI pipeline and one staging environment are needed from sprint 1: QA and human validation run on it.

1. The team

Stakeholders set direction, priorities and accept work. The product owner agent orchestrates through the backlog files in the repo. Delivery agents build; assurance agents check; DevOps keeps environments running.

2. Per-task delivery cycle

Every backlog story runs this cycle. The three red loops are logged in the backlog and return to the build step; review and QA then run again.

Escalation: a third loop on the same story, or a blocker older than one working day, is assigned to a human with a short summary from the product owner agent.

3. Sprint cycle

Two-week sprints. Accepted stories are released after human approval, and the retrospective improves the agents for the next sprint.

4. Quality gates

GateA story passes only when
Definition of ReadyUser story and acceptance criteria written; UI/UX design or HTML attached; schema and RLS policies drafted if data is involved; dependencies (integration, AI) named; sized to fit one sprint; test approach noted.
Definition of DoneAcceptance criteria met; code reviewed by the architect agent; security check and RLS policy tests passed; unit and API tests green in CI; QA test evidence linked in the story file; deployed to staging; docs and release note line updated.
AcceptedA stakeholder validated it on staging with no open feedback. Only accepted items go into a release.

5. Backlog in the repo

Backlog→Ready→In progress→In review→In QA→Awaiting validation→Accepted→Released

Files: backlog/BACKLOG.md holds epics, the sprint plan and the timeline; backlog/stories/ST-012.md holds one story (status, owner, acceptance criteria, comments); backlog/bugs/BUG-007.md holds one bug linked to its story. Status is a field at the top of each file; Git history is the audit trail.

Any review change, QA bug or feedback moves the story to Reopened with a linked bug file or comment, assigned to the owning agent. Labels route work: ui frontend backend ai integration security devops.

7. Guardrails

  • Every piece of work has a story or bug file in backlog/ and exactly one owning agent.
  • Agents work on branches; only a human merges to main and approves releases.
  • Every bug fix adds a regression test, so the same bug can’t return unnoticed.
  • Traceability: requirement → epic → story → pull request → test evidence → release.
  • QA and human validation run on staging, never on a developer build.
  • No real or production data in agent environments; test data only.
  • Row-level security is on for every table; the service-role key never reaches the browser.
  • Schema changes are Supabase migrations in Git, never manual edits in the dashboard.
  • Each retrospective updates the agent instruction files, so the team improves every sprint.
