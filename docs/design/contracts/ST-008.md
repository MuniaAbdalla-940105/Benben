# Data contract ST-008: Join to Bid — accept the auction T&Cs and lock the deposit

- Story: `backlog/stories/ST-008.md` · Owner: supabase-backend · Helpers: react-frontend, integration, ui-ux-designer, security
- Architecture: `docs/decisions/ADR-002-architecture.md` §5 (lock order), §8 (ledger) · Conventions, enums and errors: `DATA_MODEL.md`
- Uses: `ST-006.md` (`wallet_lock`, `wallet_release`), `ST-007.md` (`join_lock` payments), `ST-009.md` (`auctions`, `auction_events`)
- PRD: 2.1 (seller cannot bid), 2.3 rules 2 and 3, 3.4 steps 3–4, 3.9 **A1, A2**, 3.10 (`auction_participants`), 8.2 (consent: timestamp, IP, device, version)
- Assumptions: Q-03 (T&C v0 placeholder on staging), Q-23 (join from SCHEDULED; leave only before LIVE), Q-32 (bidder count = active participants)
- Migration: `<ts>_st008_join.sql` (sixth; it also adds the FK `payments.tc_acceptance_id` and replaces `private.process_payment_event` to add the `join_lock` branch)

**The one participant model.** A user is a **Verified Bidder for auction X** if and only if a row exists in `auction_participants` for `(X, user)` with `status = 'active'`, and its `wallet_lock_id` points to an `active` lock. Every other story (bids, chat, auto-bid, close) uses this definition.

## 2. Joinability rules (single source)

`private.auction_join_check(auction, user) returns text` (null = ok). It is evaluated **after** locking the auction row:

| Rule | Error |
|---|---|
| auction exists and `public_status <> 'hidden'` | `AUCTION_NOT_FOUND` |
| `status in ('SCHEDULED','LIVE','EXTENDED','PAUSED')` and `clock_timestamp() < ends_at` | `AUCTION_NOT_JOINABLE` |
| `seller_id <> user` (linked accounts come in ST-046) | `SELLER_CANNOT_JOIN` |
| `private.user_can_transact(user)` | `USER_BANNED` / `USER_SUSPENDED` |
| `profiles.kyc_tier >= 'T1'` | `KYC_REQUIRED` |

## 3. Functions

### 3.1 `public.join_auction(...) returns public.join_result` (authenticated)
```sql
create function public.join_auction(
  p_auction_id uuid,
  p_tc_version_id uuid,
  p_tc_accepted boolean,
  p_idempotency_key uuid,
  p_device_id text default null,
  p_app_version text default null
) returns public.join_result
language plpgsql security definer set search_path = '' ...;

create type public.join_result as (
  ok boolean, error_code text,
  participant_id uuid, alias_number int, lock_id uuid,
  already_joined boolean, replayed boolean,
  available bigint, required bigint, shortfall bigint,
  current_tc_version_id uuid, retry_after_ms int
);
```
Steps. Nothing is written unless every check passes:
1. `NOT_AUTHENTICATED` / `ANONYMOUS_NOT_ALLOWED`.
2. `p_tc_accepted` must be true → else `TC_NOT_ACCEPTED`. `p_tc_version_id` must be the current `auction` version → else `TC_VERSION_OUTDATED` (+ `current_tc_version_id`).
3. `hit_rate_limit('join', uid, 10, 60)` → `RATE_LIMITED`.
4. Cheap pre-checks without the lock: ban/suspension, `KYC_REQUIRED`.
5. `SET LOCAL lock_timeout = '2s'`, then `SELECT … FROM auctions WHERE id = p_auction_id FOR NO KEY UPDATE`. On `lock_not_available` → `BUSY_RETRY`.
6. `auction_join_check` (§2).
7. Existing participant `active` → return `ok = true, already_joined = true` with its ids. **No second lock** (AC), whatever the key.
8. `private.wallet_lock(uid, auction.deposit_amount, 'auction', 'auction', p_auction_id, 'join:' || p_idempotency_key)`. `INSUFFICIENT_BALANCE` → return it with `available`, `required = deposit_amount` and `shortfall`. The client then offers Join & Lock (§3.3). **Nothing is written** (no acceptance, no participant).
9. Insert `tc_acceptances` (`channel = 'rpc'`, IP from `private.client_ip()`, `user_agent` from the request headers).
10. Upsert the participant:
    - new: `alias_number = auctions.next_alias_number`, then `next_alias_number += 1`;
    - rejoin (status `left`): keep the alias, set `status = 'active'`, the new lock and the new acceptance, `left_at = null`.
    Then `auctions.participant_count += 1`.
11. `auction_events` (`participant_joined`, payload `{participant_id, user_id, alias_number, lock_id, via: 'wallet'}`).
12. Realtime:
    - `auction:<id>` `participants.updated` `{ participant_count }`;
    - `user:<uid>` `participation.updated` `{ auction_id, participant_id, alias_number, status: 'active' }`. This unlocks the bid controls without a reload (AC).
13. Return `ok`.

Two auctions → two calls → two separate locks (5,000 + 5,000; PRD 2.3 rule 2). This holds because locks are keyed by `(purpose, ref_id)`.

### 3.2 `public.leave_auction(p_auction_id uuid, p_idempotency_key uuid) returns public.join_result` (authenticated; Q-23)
1. Lock the auction row (as above).
2. No active participant → `NOT_JOINED`.
3. `status <> 'SCHEDULED'` → `CANNOT_LEAVE_LIVE`.
4. `wallet_release(lock_id, 'left_before_live')`.
5. Participant `status = 'left'`, `left_at`; `participant_count -= 1`.
6. `auction_events` `participant_left`; broadcasts as in §3.1 (`status: 'left'`).
7. Return `ok` with `lock_id`.

### 3.3 Join & Lock (Available < deposit), via ST-007
- The client calls `payments-create-intent` with `purpose = 'join_lock'`, `auction_id`, `tc_version_id`, `tc_accepted = true` and a new `idempotency_key`.
- `private.create_payment_intent` [ST-008 branch]:
  1. runs the `auction_join_check` rules (without locking the auction);
  2. if already an active participant → `ALREADY_JOINED`;
  3. checks the T&C rules (as §3.1 step 2);
  4. reads the wallet: if `available >= deposit` → `PAYMENT_NOT_NEEDED` (the client calls `join_auction`);
  5. sets `amount = deposit_amount − available` (≥ `payments.min_amount`, rounded up to a whole EGP);
  6. inserts the `tc_acceptances` row (`channel = 'payment_intent'`, IP and user agent passed from the Edge Function) and sets `payments.tc_acceptance_id`.
- **No lock and no participant until the webhook** (PRD 2.3 rule 3; AC).

### 3.4 `private.join_after_payment(p_payment public.payments) returns text` (called inside `process_payment_event`)
This runs after the capture has credited Available, in the **same** transaction. Lock order: payment (already locked) → auction → wallet.
1. Lock the auction row (lock timeout 2 s). If busy → raise, so the whole event processing rolls back and is retried (ST-007 §3.2).
2. Re-run `auction_join_check`, without the T&C (accepted at intent time).
3. Already an active participant → `ALREADY_JOINED`.
4. `wallet_lock(…, 'join:payment:' || payment.id)` → `INSUFFICIENT_BALANCE` if the user spent the funds in the meantime.
5. If all pass: create or reactivate the participant (`joined_via = 'payment'`, `payment_id`, `tc_acceptance_id` from the payment), plus events and broadcasts as in §3.1. Then `payments.outcome = 'credited_and_locked'`, `lock_id`.
6. Any refusal: the money **stays in Available**, `payments.outcome = 'credited_available'` and `outcome_reason = <code>`.
   - **A2, late confirmation after the auction ended:** `AUCTION_NOT_JOINABLE` → Available (AC).
   - **A1, declined:** never reaches this function. There is no capture, so there is no lock and nothing unlocks (AC).

## 4. RLS policies

**Plain words:**

| Table | anon | authenticated (owner) | staff | functions |
|---|---|---|---|---|
| `tc_versions` | SELECT published | SELECT published | SELECT all with `settings.read` | insert/publish via migration/seed (ST-045 adds the admin flow) |
| `tc_acceptances` | none | SELECT own | SELECT all with `auction.read` or `finance.read` (evidence) | INSERT via functions only; append-only |
| `auction_participants` | none (public sees only `participant_count` and aliases in bids) | SELECT own rows | SELECT all with `auction.read` | write via `join_auction` / `leave_auction` / `join_after_payment` only |

```sql
alter table public.tc_versions enable row level security;
revoke all on public.tc_versions from anon, authenticated;
grant select on public.tc_versions to anon, authenticated;
create policy tc_versions_public_select on public.tc_versions
  for select to anon, authenticated using (published_at is not null);

alter table public.tc_acceptances enable row level security;
revoke all on public.tc_acceptances from anon, authenticated;
grant select on public.tc_acceptances to authenticated;
create policy tc_acceptances_owner_select on public.tc_acceptances
  for select to authenticated using (user_id = (select auth.uid()));
create policy tc_acceptances_staff_select on public.tc_acceptances
  for select to authenticated
  using ((select private.has_permission('auction.read')) or (select private.has_permission('finance.read')));
create trigger tc_acceptances_append_only before update or delete on public.tc_acceptances
  for each row execute function private.forbid_mutation();

alter table public.auction_participants enable row level security;
revoke all on public.auction_participants from anon, authenticated;
grant select on public.auction_participants to authenticated;
create policy auction_participants_owner_select on public.auction_participants
  for select to authenticated using (user_id = (select auth.uid()));
create policy auction_participants_staff_select on public.auction_participants
  for select to authenticated using ((select private.has_permission('auction.read')));

revoke execute on function public.join_auction(uuid, uuid, boolean, uuid, text, text) from public, anon;
grant execute on function public.join_auction(uuid, uuid, boolean, uuid, text, text) to authenticated;
revoke execute on function public.leave_auction(uuid, uuid) from public, anon;
grant execute on function public.leave_auction(uuid, uuid) to authenticated;

alter table public.payments add constraint payments_tc_acceptance_fk
  foreign key (tc_acceptance_id) references public.tc_acceptances(id);
```

## 7. Backend tests

pgTAP:
1. Happy path: a T1 user with 20,000 EGP joins a LIVE auction → 1 lock of 5,000, a participant with `alias_number = 1`, `participant_count = 1`, an acceptance row with IP, user agent, device and version, an `auction_events` row, and both broadcasts.
2. **Double join:** the same call again (same key, and also a different key) → `already_joined = true`; still 1 lock and 1 participant; balances unchanged.
3. **Insufficient balance:** 3,000 available → `INSUFFICIENT_BALANCE` with `shortfall = 200000`; **0** acceptances, participants or locks written.
4. **Two auctions:** 10,000 available, join A and B → 2 locks, `locked = 10000`, `available = 0`. A third join → `INSUFFICIENT_BALANCE`.
5. **Seller self-join** → `SELLER_CANNOT_JOIN` (via RPC and via `join_lock` intent creation).
6. **Banned / suspended** → `USER_BANNED` / `USER_SUSPENDED`. **T0 user** → `KYC_REQUIRED`.
7. T&C: `p_tc_accepted = false` → `TC_NOT_ACCEPTED`; an old version id → `TC_VERSION_OUTDATED`.
8. Status rules: SCHEDULED → join ok; LIVE → ok; ENDED, or `ends_at` passed while still LIVE → `AUCTION_NOT_JOINABLE`; DRAFT → `AUCTION_NOT_FOUND`.
9. Leave: in SCHEDULED → lock released, `status = left`, count −1; rejoin keeps the same alias and creates a new lock. Leave in LIVE → `CANNOT_LEAVE_LIVE`.
10. **Join & Lock** (with the ST-007 mock): 2,000 available, deposit 5,000 → intent amount 3,000. `success` webhook → capture 3,000, then lock 5,000; participant active; outcome `credited_and_locked`.
11. **A1:** a declined Join & Lock → no lock, no participant, no ledger txn.
12. **A2 late:** the auction moved to ENDED before the webhook → capture to Available only; `outcome = credited_available`, `outcome_reason = 'AUCTION_NOT_JOINABLE'`; no participant.
13. Join & Lock when already joined by the time the webhook arrives → `credited_available`, `ALREADY_JOINED`, still only 1 lock.
14. RLS: user A sees only A's participant rows and acceptances. anon → no participant rows. User A cannot insert or update `auction_participants` or `tc_acceptances` directly (permission denied). An update or delete on `tc_acceptances` by the service role → `APPEND_ONLY`.

Concurrency (Node harness):
15. The same user fires `join_auction` 10× in parallel with different keys → exactly 1 lock and 1 participant.
16. 50 different users join the same auction in parallel → 50 distinct alias numbers 1..50, `participant_count = 50`, 50 locks.
