## 2. Increment functions (ship in the st009 migration)

### 2.1 `public.increment_for(p_table_id uuid, p_price bigint) returns bigint`
`STABLE`, `SECURITY INVOKER` (the bands are public):
```sql
select b.increment from public.increment_bands b
where b.table_id = p_table_id and b.from_amount <= p_price
order by b.from_amount desc limit 1;
```

### 2.2 `public.auction_min_next_bid(p_table_id uuid, p_starting_price bigint, p_current_price bigint, p_bid_count int) returns bigint`
```sql
select case when p_bid_count = 0 or p_current_price is null
            then p_starting_price                                         -- Q-20
            else p_current_price + public.increment_for(p_table_id, p_current_price) end;  -- Q-21: band of current price
```
Both functions are granted to anon and authenticated. **The same functions** are used by `auction_public`, `get_auction_live_state` and `place_bid`, so the UI and the server always agree.

Band boundary examples (EGP; piasters in the tests):

| Current price | Increment | Minimum next bid |
|---|---|---|
| no bids, start 4,500,000 | — | 4,500,000 |
| 999,999 | 10,000 | 1,009,999 |
| 1,000,000 | 25,000 | 1,025,000 |
| 4,999,999 | 25,000 | 5,024,999 |
| 5,000,000 | 50,000 | 5,050,000 |
| 9,999,999 | 50,000 | 10,049,999 |
| 10,000,000 | 100,000 | 10,100,000 |

Amounts are whole EGP, so a current price like 999,999 EGP is valid (Q-21: any whole EGP ≥ the minimum).

## 3. `public.place_bid(...)`

```sql
create type public.place_bid_result as (
  ok boolean,
  error_code text,            -- null when ok; DATA_MODEL §6 codes
  replayed boolean,           -- true when the idempotency key matched an existing bid
  bid_id uuid,
  seq bigint,                 -- this bid's seq (ok) or the auction's current bid_seq (rejected)
  amount bigint,
  server_ts timestamptz,      -- this bid's server time (ok) or clock_timestamp() (rejected)
  current_price bigint,
  min_next_bid bigint,        -- always set when the auction exists: the "new minimum is X"
  current_increment bigint,
  bid_count int,
  ends_at timestamptz,
  is_leading boolean,
  retry_after_ms int,         -- RATE_LIMITED, BUSY_RETRY
  max_allowed bigint          -- BID_TOO_HIGH
);

create function public.place_bid(
  p_auction_id uuid,
  p_amount bigint,
  p_idempotency_key uuid,
  p_expected_seq bigint default null   -- the bid_seq the client last saw
) returns public.place_bid_result
language plpgsql volatile security definer set search_path = '' as $$ … $$;

revoke execute on function public.place_bid(uuid, bigint, uuid, bigint) from public, anon;
grant execute on function public.place_bid(uuid, bigint, uuid, bigint) to authenticated;
```
`place_bid` is a thin wrapper: it resolves `auth.uid()`, rejects anonymous JWTs and calls `private.place_bid_core(p_user_id, p_auction_id, p_amount, p_idempotency_key, p_expected_seq, p_type => 'manual', p_auto_bid_id => null)`. The core is reused by auto-bid (ST-015), the seed and the load-test harness.

### 3.1 Algorithm (`private.place_bid_core`)
Validation runs in this **fixed order**, so that the error precedence is deterministic. Steps 1–6 run **before** the lock, to keep spam off the hot row.

| # | Step | On failure |
|---|---|---|
| 1 | `p_user_id` not null and not anonymous | `NOT_AUTHENTICATED` / `ANONYMOUS_NOT_ALLOWED` |
| 2 | `p_amount > 0 and p_amount % 100 = 0` | `INVALID_AMOUNT` |
| 3 | Idempotency pre-check: a bid with `(user_id, idempotency_key)` exists → same auction **and** amount → return it with `replayed = true` and the current auction figures. Different → `DUPLICATE_REQUEST` | — |
| 4 | `private.hit_rate_limit('bid', user || ':' || auction, limit, window)` | `RATE_LIMITED` + `retry_after_ms` |
| 5 | `private.user_can_transact(user)` | `USER_BANNED` / `USER_SUSPENDED` |
| 6 | Active participant for `(auction, user)` (status `active`) | `NOT_PARTICIPANT` |
| 7 | `SET LOCAL lock_timeout = '2s'`; `SELECT … FROM auctions WHERE id = p_auction_id FOR NO KEY UPDATE` | not found or hidden → `AUCTION_NOT_FOUND`; `lock_not_available` → `BUSY_RETRY` (`retry_after_ms = 200`) |
| 8 | Idempotency re-check under the lock (a concurrent duplicate may just have committed) | replay as in step 3 |
| 9 | `v_now := clock_timestamp()` (**after** the lock: this is the bid's server time, ADR-002 §5) | — |
| 10 | `status = 'PAUSED'` | `AUCTION_PAUSED` |
| 11 | `status not in ('LIVE','EXTENDED')` | `AUCTION_NOT_LIVE` (SCHEDULED) or `AUCTION_ENDED` (any post-live state) |
| 12 | `v_now >= ends_at` (**lazy end check**: the sweeper may not have run yet; A6, server state rules) | `AUCTION_ENDED` |
| 13 | Re-read the participant row (it must still be `active`) | `NOT_PARTICIPANT` |
| 14 | `current_leader_participant_id = my participant` (no self-outbidding, PRD 3.5) | `ALREADY_LEADING` |
| 15 | `v_min := auction_min_next_bid(...)`. If `p_amount < v_min`: **`OUTBID`** when `p_expected_seq is not null and p_expected_seq < auctions.bid_seq` (someone bid after what the client saw; **A5**), otherwise `BID_TOO_LOW` | `OUTBID` / `BID_TOO_LOW` + `min_next_bid` |
| 16 | `p_amount > v_min + max_increments_above_min × increment_for(current)` | `BID_TOO_HIGH` + `max_allowed` |
| 17 | `v_seq := bid_seq + 1`. Insert the bid (`server_ts = v_now`). On `unique_violation` of `(user_id, idempotency_key)` → replay | — |
| 18 | Update the auction: `current_price = p_amount`, `current_leader_participant_id`, `current_leader_alias_number`, `bid_count += 1`, `bid_seq = v_seq`, `updated_at = v_now`. **[ST-014 slot]**: if `ends_at − v_now <= extension_window_s` and the cap allows → `ends_at = v_now + extension_s`, `extensions_count += 1`, and send `auction.extended` | — |
| 19 | `private.log_auction_event(auction, 'bid', 'user', user, {bid_id, seq, amount, participant_id, user_id})` | — |
| 20 | `realtime.send(payload, 'bid.placed', 'auction:' || auction_id, true)` (transactional: it is published only if the bid commits) | — |
| 21 | Return `ok = true`, `is_leading = true` and the new `min_next_bid` | — |

Rejected bids write **nothing** except the rate-limit counter (which commits, because rejections are returned, not raised). The lock hold time is steps 7–21, with no I/O beyond this database; the target is < 5 ms.

### 3.2 Edge cases resolved explicitly
- **A5 (two bids in the same millisecond):** both callers queue on the row lock. The first to acquire it gets `seq = n+1` and wins. The second re-validates against the new state. If its amount is now below the new minimum and it sent `p_expected_seq = n`, it gets `OUTBID` with `min_next_bid` ("Outbid, new minimum is X"). If its amount still clears the new minimum, it is accepted as `seq = n+2` (the rule is amount ≥ current + increment). The outcome is deterministic: the lock order defines it, and `seq`, `server_ts` and commit order agree.
- **A6 (the bidder disconnects in the final minute):** nothing is held client-side. A bid that reaches the server at or after `ends_at` gets `AUCTION_ENDED`. A reconnecting client resyncs through `get_auction_live_state` (ST-011 §6). No compensation.
- **Double tap:** the same idempotency key → one bid. The second call returns the first result (`replayed = true`).
- **Retraction:** there is no RPC, no grant and no trigger path (§1.1). An admin void comes in ST-026 with maker-checker.

## 4. RLS and grants

**Plain words:**

| Object | anon | authenticated | staff | functions |
|---|---|---|---|---|
| `bids` | SELECT granted columns for publicly visible auctions | same (own bids found by `participant_id`) | SELECT all with `auction.read` | INSERT only via `place_bid_core`; UPDATE only via the ST-026 void; never DELETE |
| `bid_public` (view) | yes | yes | | |
| `place_bid` | **no EXECUTE** | EXECUTE | | |

```sql
alter table public.bids enable row level security;
revoke all on public.bids from anon, authenticated;
grant select (id, auction_id, participant_id, bidder_alias_number, amount, seq, type, server_ts, status)
  on public.bids to anon, authenticated;
create policy bids_public_select on public.bids
  for select to anon, authenticated using ((select private.auction_is_public(auction_id)));
create policy bids_staff_select on public.bids
  for select to authenticated using ((select private.has_permission('auction.read')));
create trigger bids_guard before update or delete on public.bids
  for each row execute function private.guard_bid_mutation();
```
The `(select private.auction_is_public(auction_id))` form is evaluated per row. Bid history reads are capped at 50 rows per page and filtered by `auction_id`, so the cost is bounded.

## 5. Realtime channel `auction:<auction_id>` (private; receive-only for clients; policy in ST-009 §4)

All payloads are JSON with `v: 1`. Amounts are piasters and times are ISO-8601 UTC with microseconds. **No user ids.**

### `bid.placed` (this story)
```json
{
  "v": 1,
  "auction_id": "6f1c…",
  "bid_id": "a2d4…",
  "seq": 42,
  "amount": 452500000,
  "bidder_alias_number": 7,
  "leader_participant_id": "c0ff…",
  "type": "manual",
  "server_ts": "2026-11-10T12:00:00.123456Z",
  "current_price": 452500000,
  "current_increment": 2500000,
  "min_next_bid": 455000000,
  "bid_count": 42,
  "ends_at": "2026-11-11T09:00:00.000000Z",
  "extensions_count": 0
}
```

### Other events on the same channel (defined here so the shape is stable)
| Event | Story | Payload |
|---|---|---|
| `auction.extended` | ST-014 | `{ v, auction_id, seq, previous_ends_at, ends_at, extensions_count, server_ts }` |
| `auction.state_changed` | ST-013 | `{ v, auction_id, status /* public */, ends_at, server_ts }` |
| `participants.updated` | ST-008 | `{ v, auction_id, participant_count, server_ts }` |
| `bid.voided` | ST-026 | `{ v, auction_id, seq, bid_id, current_price, min_next_bid, leader_participant_id, bid_count, server_ts }` |

Ordering contract: `seq` increases by exactly 1 per accepted bid. A client that receives `seq > last_seq + 1` has missed messages and **must resync** (ST-011 §6). Duplicate or older `seq` values are ignored.

Latency measurement (AC, PRD 8.4): `receive_time − server_ts`, using the time-sync offset. The staging dashboard script `tools/loadtest/probe.ts` subscribes one probe client and logs p50/p95 per bid. The full test is ST-012.

## 7. Backend tests

pgTAP, one test per validation rule (AC: "every validation rule and each increment band boundary"):
1. First bid = starting price → ok, `seq = 1`. First bid = starting − 100 → `BID_TOO_LOW` with `min_next_bid = starting`.
2. Each band boundary in §2 (7 rows): amount = min → ok; amount = min − 100 → `BID_TOO_LOW`.
3. Amount not a whole EGP (e.g. `450000050`) → `INVALID_AMOUNT`; `0` or negative → `INVALID_AMOUNT`.
4. Not a participant (T1, never joined) → `NOT_PARTICIPANT`. A participant who left (`status = left`) → `NOT_PARTICIPANT`.
5. SCHEDULED → `AUCTION_NOT_LIVE`; PAUSED → `AUCTION_PAUSED`; ENDED → `AUCTION_ENDED`; LIVE with `ends_at` in the past (sweeper not run) → `AUCTION_ENDED`; DRAFT or unknown id → `AUCTION_NOT_FOUND`.
6. The leader bids again → `ALREADY_LEADING`.
7. Banned or suspended (with an active participation from before the ban) → `USER_BANNED` / `USER_SUSPENDED`.
8. Idempotency: the same key twice → 1 bid, the second `replayed = true` with the same `bid_id` and `seq`. The same key with another amount → `DUPLICATE_REQUEST`.
9. `OUTBID` vs `BID_TOO_LOW`: with `p_expected_seq = bid_seq − 1` and a low amount → `OUTBID`; with `p_expected_seq = bid_seq` → `BID_TOO_LOW`; with no `p_expected_seq` → `BID_TOO_LOW`.
10. `BID_TOO_HIGH` above the cap, with `max_allowed` returned. Exactly at the cap → ok.
11. Rate limit: the 11th call within 10 s → `RATE_LIMITED`; the counter persists although the call was rejected.
12. Accepted bid side effects: `auctions.current_price`, leader, `bid_count` and `bid_seq` updated; 1 `auction_events` row of type `bid`; 1 row in `realtime.messages` with topic `auction:<id>` and event `bid.placed` whose payload matches §5 (JSON schema check), with no `user_id` key.
13. Rejected bid → no `bids` row, no event and no `realtime.messages` row.
14. RLS: authenticated `insert into bids` → permission denied; `update bids set amount` → denied; `delete` → denied. The service role deleting → `APPEND_ONLY`. anon `select user_id from bids` → permission denied. anon `bid_public` for a DRAFT auction → 0 rows. anon `rpc('place_bid')` → permission denied.
15. Retraction: no function in `public` other than `place_bid` writes to `bids` (`pg_proc` catalogue check against the RPC allow-list).

Concurrency (`supabase/tests/concurrency/st010_bids.test.ts`, Node + `pg`, 50 connections; story test plan):
16. **A5:** two participants send `amount = min_next_bid` with the same `p_expected_seq` at the same instant (released by a barrier) → exactly 1 `ok`, 1 `OUTBID` with the new minimum; `bid_count = 1`.
17. 50 parallel bids from 25 participants with increasing amounts, repeated over 20 rounds → `seq` values are exactly `1..N` with no gaps or duplicates; `server_ts` is non-decreasing in `seq` order; `amount` is strictly increasing in `seq` order; `auctions.current_price = max(amount)`; there is exactly one leader, and no participant holds two consecutive seqs (no self-outbid).
18. 10 parallel calls with **the same** idempotency key → 1 bid, 9 replays.
19. The lock does not block chat or joins: while a bid transaction holds the row (`pg_sleep` in a test-only wrapper), an insert into a child table with an FK to `auctions` (e.g. `auction_events`) does not wait (`FOR NO KEY UPDATE` vs `KEY SHARE`).
20. `lock_timeout`: hold the auction row for 3 s from another session → `place_bid` returns `BUSY_RETRY` within ~2 s, with nothing written.
