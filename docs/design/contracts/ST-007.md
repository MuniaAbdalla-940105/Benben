## 3. Functions and Edge Functions

**Edge Function → database (ADR-006).** `private` is not exposed through the API. Every `private.*` function that an Edge Function below calls is reached through a `public.svc_<same name>` wrapper:
- `SECURITY DEFINER`, `SET search_path = ''`, the same arguments and return type;
- `EXECUTE` for `service_role` only, and never on `tools/ci/rpc-allowlist.txt`.

The wrappers in this story are:
- `svc_create_payment_intent`
- `svc_attach_gateway_order`
- `svc_cancel_payment`
- `svc_process_payment_event`
- `svc_claim_due_inquiries`
- the wrappers `mock-gateway` needs to read and write `private.mock_gateway_transactions` (`svc_mock_gateway_*`)

The step text below names the `private` function, which is the implementation.

### 3.1 Edge Function `payments-create-intent` (user JWT)
**Request:**
```json
{ "purpose": "topup" | "join_lock",
  "method": "card" | "wallet",
  "amount": 500000,                 // topup only; ignored for join_lock (server computes it)
  "auction_id": "uuid",             // join_lock only
  "tc_version_id": "uuid",          // join_lock only [ST-008]
  "tc_accepted": true,              // join_lock only [ST-008]
  "idempotency_key": "uuid",
  "device_id": "string",
  "return_url": "https://…/auctions/<id>?payment=<placeholder>" }
```
**Steps:**
1. Verify the JWT and take `client_ip` from `x-forwarded-for` on the incoming request.
2. Call `private.create_payment_intent(user_id, purpose, method, amount, auction_id, tc_version_id, tc_accepted, idempotency_key, device_id, client_ip, user_agent)` with the service role. It returns `private.payment_intent_result (ok, error_code, payment_id, amount, status, checkout_url, replayed, details jsonb)`.
3. If `replayed` and a `checkout_url` exists → return it. No second gateway call.
4. `PaymentGateway.createIntent({ merchantOrderId: payment_id, amount, currency: 'EGP', method, customer: { phone }, returnUrl })`, then `private.attach_gateway_order(payment_id, gateway, gateway_order_id, checkout_url)`, which sets `next_inquiry_at = now() + 15 s` and `inquiry_until`.
5. If the adapter fails → `private.cancel_payment(payment_id, 'GATEWAY_UNAVAILABLE')` and return 502.

**Checks inside `create_payment_intent`**, in this order. Business errors are returned, not raised:

| # | Check | Error |
|---|---|---|
| 1 | user exists and is not anonymous | `NOT_AUTHENTICATED` |
| 2 | `private.user_can_transact` | `USER_BANNED` / `USER_SUSPENDED` |
| 3 | `kyc_tier >= T1` (all payments; AML-conservative, see the risks list) | `KYC_REQUIRED` |
| 4 | rate limit `payment:intent` 5 per 10 min per user | `RATE_LIMITED` |
| 5 | same `(user_id, idempotency_key)`: same params → replay; different params | `DUPLICATE_REQUEST` |
| 6 | `topup`: `amount` ≥ `payments.min_amount` and `amount % 100 = 0` | `INVALID_AMOUNT` |
| 7 | **[ST-008]** `join_lock`: auction joinable, not the seller, not already joined, T&C accepted and current, Available < deposit; then `amount = deposit − available` | `AUCTION_NOT_FOUND`, `AUCTION_NOT_JOINABLE`, `SELLER_CANNOT_JOIN`, `ALREADY_JOINED`, `TC_NOT_ACCEPTED`, `TC_VERSION_OUTDATED`, `PAYMENT_NOT_NEEDED` |
| 8 | insert `payments` (status `pending`). **[ST-008]** Record the T&C acceptance and set `tc_acceptance_id` | — |

**Response:** `{ ok: true, data: { payment_id, amount, status: 'pending', checkout_url } }`.

### 3.2 Edge Function `payments-webhook` (no JWT; `verify_jwt = false` in `config.toml`)
1. Read the raw body as bytes. **Do not parse before verifying.**
2. `adapter.verifyWebhook(rawBody, headers)`:
   - mock: header `x-benben-timestamp` + `x-benben-signature: sha256=<hex>` over `${timestamp}.${rawBody}` with `PAYMENTS_HMAC_SECRET`. The timestamp must be within ±300 s (replay protection). Constant-time compare.
   - Paymob: its HMAC-SHA512 over the documented field order.
3. Insert into `payment_webhook_events` (service role), **always**, with `signature_valid`.
   - Invalid signature → `processing_status = 'rejected_signature'`, write `audit_logs` `payment.webhook_rejected`, return **401** `INVALID_SIGNATURE`. Nothing else changes (AC).
   - Unique conflict on `(gateway, gateway_event_id)` → return 200 `duplicate_event`.
4. Call `private.process_payment_event(event_id)`.
   - Returns the processing status → HTTP 200.
   - On `BUSY_RETRY` or an exception → the event stays `received`/`error`, and the function returns 500 so the gateway retries. The inquiry sweep also retries events that stay stuck in `received` for more than 60 s.

### 3.3 `private.process_payment_event(p_event_id uuid) returns text` (service role only)
1. Load the event, `FOR UPDATE`. If it is not `received`/`error`, return its status (idempotent).
2. Find the payment by `gateway_order_id` and lock it, `FOR UPDATE` (lock order: payments first). If not found → `ignored`, with an audit row `payment.unknown_order`.
3. For `payment.succeeded`, the amount and currency must equal the payment's. Otherwise → `flagged`, error `AMOUNT_MISMATCH`, `outcome = 'flagged_mismatch'`, audit row, **no ledger posting**. Finance resolves it.
4. Apply the event type:

| Event | Payment state | Effect |
|---|---|---|
| `succeeded` | `pending`, `declined` or `expired` | `status = paid`, `gateway_txn_id`, `paid_at`. If a pending posting exists → `wallet_pending_reverse`. Then `wallet_credit_capture` (key `payment:<id>:capture`) → `outcome = credited_available`. **[ST-008]** If `purpose = join_lock` → `private.join_after_payment(payment)`: success → `outcome = credited_and_locked`, `lock_id`; refusal → stays `credited_available` with `outcome_reason` (see ST-008 §3.3) |
| `succeeded` | `paid`, **same** `gateway_txn_id` | no-op → `duplicate_event` (**A3, redelivery**) |
| `succeeded` | `paid`, **different** `gateway_txn_id` | **A3, double charge**: insert a child payment (`parent_payment_id`, same user/purpose/amount, `status = paid`, `outcome = refund_required`, new `gateway_txn_id`), then `wallet_duplicate_capture` (D gateway_clearing / C **refunds_payable**, so it never reaches the user's Available), then audit `payment.duplicate_capture`. The refund itself is executed by ST-044 |
| `declined` | `pending` | `status = declined`, `decline_reason_code`, `decline_message`. Reverse any pending posting. **No other money moves, and no lock** (**A1**) |
| `declined` | `paid` | `ignored` (audit) |
| `pending` | `pending` and no pending posting yet | `wallet_pending_add` (async methods). The user sees it in the Pending bucket |

5. Mark the event `processed`, link `payment_id`, set `processed_at`.
6. Send realtime `user:<uid>` `payment.updated` (and `wallet.updated` from `ledger_post`).

### 3.4 Edge Function `payments-inquiry-sweep` (A2)
- Scheduled by `pg_cron` every 15 s: `select private.invoke_edge('payments-inquiry-sweep')` (pg_net POST, header `x-cron-secret` from Vault). Requests with a wrong secret → 401.
- `private.claim_due_inquiries(p_limit int default 50)` selects payments with `status = 'pending' and next_inquiry_at <= now() and now() < inquiry_until`, `FOR UPDATE SKIP LOCKED`. It sets `next_inquiry_at = now() + 15 s` and `inquiry_attempts += 1`.
- For each one, `adapter.inquire(gateway_order_id)`. A terminal answer inserts a synthetic `payment_webhook_events` row (`source = 'inquiry'`, `signature_valid = true` because it came from an authenticated API call; `gateway_event_id = 'inq:<txn_id>'`), then calls `process_payment_event`.
- It also re-runs `process_payment_event` for events stuck in `received`/`error` for more than 60 s, at most 5 tries each. After that → `error` and a Finance alert (ST-043).
- After `inquiry_until` (10 min) the payment **stays `pending`**: polling stops, and the UI says "still pending, we will notify you". A late webhook is still processed normally (late confirmation → Available, never a lock for an ended auction, ST-008). Daily reconciliation (ST-043) catches anything left.

### 3.5 `mock-gateway` Edge Function (local and staging only; the prod deploy must fail if it is included)
**Environment guard (ADR-006 §3.2).** Every route first runs `requireNonProduction(admin)` from `supabase/functions/_shared/env.ts`. The request goes ahead only if the function secret `APP_ENV` equals `public.svc_runtime_env()` and the value is not `production`. Unset or unknown `APP_ENV`, an RPC error, or a mismatch → 403 `{ ok: false, error_code: 'NOT_ALLOWED_IN_ENV' }`. Nothing is read or written and no webhook is sent. The `payments-*` functions do not run this guard: they are production functions, and `PAYMENTS_PROVIDER` selects the adapter.

| Route | Caller | Behaviour |
|---|---|---|
| `POST /intents` | adapter | create a mock transaction → `{ gateway_order_id: 'mock_<uuid>', checkout_url: '<WEB_URL>/dev/mock-checkout/<gateway_order_id>' }` |
| `POST /simulate` | PAY-01 page (user JWT; the order must belong to the caller) or QA (`x-qa-token`) | `{ gateway_order_id, scenario, decline_reason?, delay_s? }` |
| `GET /inquiry/:gateway_order_id` | adapter | `{ status: 'pending'|'succeeded'|'declined', gateway_txn_id?, amount, currency }` |

| Scenario | What the mock does |
|---|---|
| `success` | one signed `payment.succeeded` webhook (txn `T1`) |
| `decline` | one signed `payment.declined` with `decline_reason` (default `insufficient_funds`) |
| `delay` | no webhook; inquiry says `pending` until `delay_s` (default 45 s), then `succeeded`. Sends the webhook after `delay_s + 60 s`, so inquiry wins |
| `delay_no_webhook` | as `delay`, but never sends a webhook (inquiry-only confirmation) |
| `late` | inquiry stays `pending` for 11 min (past `inquiry_until`), then the webhook arrives (tests late confirmation) |
| `duplicate_event` | the same `success` webhook delivered twice (same event id), plus a third copy with a new event id and the same `T1` |
| `double_charge` | `success` with `T1`, then a second `success` with `T2` for the same order |
| `invalid_signature` | `success` signed with a wrong key |
| `amount_mismatch` | `success` with `amount − 100` |

### 3.6 Adapter interface
```ts
// supabase/functions/_shared/adapters/payments/types.ts
export interface CreateIntentInput { merchantOrderId: string; amount: number; currency: 'EGP'; method: 'card'|'wallet'|'fawry'; customer: { phone: string }; returnUrl: string }
export interface NormalisedEvent { gatewayEventId: string | null; gatewayOrderId: string; gatewayTxnId: string | null;
  type: 'payment.succeeded'|'payment.declined'|'payment.pending'|'payment.refunded'; amount: number; currency: 'EGP';
  declineReason?: string; declineMessage?: string }
export interface PaymentGateway {
  readonly name: 'mock' | 'paymob';
  createIntent(i: CreateIntentInput): Promise<{ gatewayOrderId: string; checkoutUrl: string }>;
  verifyWebhook(rawBody: Uint8Array, headers: Headers): Promise<boolean>;
  parseEvent(rawBody: Uint8Array): NormalisedEvent;
  inquire(gatewayOrderId: string): Promise<NormalisedEvent | { type: 'pending' }>;
  refund?(gatewayTxnId: string, amount: number): Promise<{ refundId: string }>;   // ST-044
}
```
Secrets: `PAYMENTS_PROVIDER`, `PAYMENTS_HMAC_SECRET`, `MOCK_GATEWAY_URL` (non-prod), `PAYMOB_API_KEY` / `PAYMOB_HMAC` (later). They live in Edge Function secrets only, never in `VITE_*` and never in the DB except the cron secret in Vault.

## 7. Backend tests (Deno tests for the Edge Functions plus pgTAP; ledger assertions after every scenario)

| # | Scenario | Expected |
|---|---|---|
| 1 | `success` (topup 1,000 EGP) | payment `paid`; one `payment_capture` txn; `available += 100000`; trial balance ok; one `payment.updated` |
| 2 | Redirect only (no webhook, `delay_no_webhook` before the inquiry runs) | payment still `pending`; **no ledger rows** (PRD 2.3 rule 1) |
| 3 | **A1** `decline` | `declined`, `decline_reason_code` set; 0 ledger txns; a new intent with a new key is allowed |
| 4 | **A2** `delay` | `pending` until the inquiry returns `succeeded`; credited within ≤ 15 s of `delay_s`; the later webhook → `duplicate_event`, no second credit |
| 5 | **A2** `late` | polling stops at 10 min with the payment still `pending`; the webhook at 11 min credits Available |
| 6 | **A3** `duplicate_event` | exactly 1 capture; events 2 and 3 → `duplicate_event` |
| 7 | **A3** `double_charge` | parent `paid` with 1 capture to Available; child `refund_required` with 1 `duplicate_capture` to `refunds_payable`; user Available rises **only once** |
| 8 | `invalid_signature` | 401, event stored with `rejected_signature`, payment unchanged, audit row |
| 9 | Stale timestamp (> 300 s) with a valid HMAC | 401 |
| 10 | `amount_mismatch` | `flagged`, no ledger txn, audit row |
| 11 | Idempotent intent: same key twice | one payment row, one gateway `createIntent` call |
| 12 | Same key, different amount | `DUPLICATE_REQUEST` |
| 13 | Unique `gateway_txn_id`: a raw insert of a second payment with the same txn id | fails |
