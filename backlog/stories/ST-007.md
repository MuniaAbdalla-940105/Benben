## Story
As a bidder, I want to pay my deposit by card or mobile wallet and have it credited only when the payment is really confirmed, so that my money is safe and the platform is never fooled by a fake redirect.

## Acceptance criteria
- Given a payment intent (top-up or Join & Lock), when it is created, then a `payments` row is stored with amount, idempotency key and status `pending`, and the user is sent to the mock checkout. Assumption (Q-09): Paymob behind an adapter; cards and wallets first.
- Given the mock checkout succeeds, when the client is redirected back, then nothing is credited from the redirect alone (PRD 2.3 rule 1).
- Given the mock gateway sends a webhook, when its HMAC signature is valid, then the payment becomes `paid` and the ledger is credited (to Available, or straight into a lock for Join & Lock) in one transaction (PRD 8.2).
- Given a webhook with an invalid signature, when received, then it is rejected, logged, and nothing changes.
- Given a decline (A1), when the webhook arrives, then no money moves, the gateway reason is stored and shown, and the user can retry with another method.
- Given a delayed webhook (A2), when the client shows "Payment pending", then the server polls the gateway inquiry API every 15 s for up to 10 min and confirms on success.
- Given the same `gateway_txn_id` arrives twice (A3), when processed, then only one ledger credit exists (unique constraint) and the duplicate is flagged for auto-refund.
- Given the mock, when configured, then it can simulate success, decline, delay, duplicate and invalid signature on demand for QA (ADR-001).
- Given `raw_webhook`, when stored, then it is readable only by Finance and server functions.
