## Story
As the delivery team, I want a working repo, CI pipeline and Supabase staging project from day one, so that every story can be built on a branch, tested automatically and validated on staging.

## Acceptance criteria
- Given a fresh clone, when a developer runs the documented setup commands, then the React app (Vite) and a local Supabase stack start with no manual dashboard steps.
- Given a pull request on a branch `st-###-*`, when CI runs, then it executes lint, type-check, Vitest unit tests, Supabase migration apply on a clean database, and database (RLS) tests, and blocks merge on any failure.
- Given a migration in `supabase/migrations/`, when it is merged by a stakeholder, then the pipeline applies it to the staging project; no schema change is made by hand in the dashboard.
- Given the staging project, when the frontend is deployed, then it is reachable on a stable staging URL and uses only the anon key in the browser; the service-role key exists only in CI secrets and Edge Function secrets.
- Given the generated TypeScript types, when the schema changes, then CI fails if `supabase gen types` output is out of date.
- Given staging, when it is seeded, then it holds synthetic data only (no real or production data). Assumption (Q-74): seed uses public area names for New Cairo and Sheikh Zayed.
- Given Supabase plan and region are not yet decided, when staging is created, then it uses a paid plan in the nearest available region and the choice is recorded in an ADR. Assumption (Q-44, Q-06).
